# 跨技术栈产品逆向工程指南

**证据成熟度：`proposed`**

**适用范围：** 用于在明确授权下，以产品与业务问题为主线组织 Delphi、Web、Java、.NET 及相关数据与基础设施的黑盒、灰盒或白盒逆向工程；不替代法律、合规、安全、数据或系统所有者的批准，也不自动证明目标产品事实。

## 目的

本指南帮助团队把遗留产品的界面、代码、数据与运行行为还原为可追溯、可验证、可交付的产品知识。重点不是逐文件翻译，而是建立“业务问题—运行证据—跨栈实现—结论—验证”的证据链，让项目负责人能控制范围与风险，让执行团队能按同一套门槛协作。

这是一个 Guide，用于组织工作流与证据，而不是一个会因结构校验通过就自动获得验证状态的 Pattern。可复用方法或建议只有满足[贡献规范](../../CONTRIBUTING.md)中的独立证据要求后，才能晋升为 Pattern、Anti-pattern 或 Experiment。

## 适用受众

### 给项目负责人

使用本指南确定逆向目标、优先级、完成定义和安全边界；根据主张状态、置信度和证据引用判断哪些产品主张可以用于决策，哪些仍需取证。先走下方五分钟选型流程，再按阅读顺序建立共同契约，最后按执行顺序分配阶段负责人。

### 给执行团队与 AI Agent

使用本指南统一采集证据、追踪跨技术栈调用链、区分观察与推断，并在发布前执行同一个验证入口。任何自动化都必须服从数据授权、最小访问和人工复核边界。

## 五分钟选型流程

**本节说明：** 证据成熟度：`proposed`。本节的选型步骤和任务说明是待跨项目验证的工作流建议，不代表已经形成 Pattern。

| 时间 | 判断 | 选择 |
| --- | --- | --- |
| 0–1 分钟 | 目标是回答“产品做什么”还是“代码怎么做”？ | 前者以业务流程和行为证据为主，后者补充代码与数据追踪；两者都要写明决策用途 |
| 1–2 分钟 | 是否能安全运行原系统？ | 能运行则设计最小可重复场景；不能运行则标注限制，只做静态证据链，不猜测运行结果 |
| 2–3 分钟 | 问题是否跨越界面、服务和数据层？ | 跨层问题使用端到端追踪；单层问题仍记录上下游假设，避免局部结论越界 |
| 3–4 分钟 | 当前采用的方法或建议有多宽的验证基础？ | 从下方四个标签中选择其支撑证据成熟度；不确定时使用较低成熟度 |
| 4–5 分钟 | 交付物面向决策还是执行？ | 决策交付突出范围、风险和置信度；执行交付补齐定位、复现步骤与验证命令 |

选型结束时应得到一条短任务说明：目标问题、允许的数据源、运行权限、方法或建议的目标成熟度、负责人和完成定义。缺少其中任何一项，先补齐边界再取证。

## 证据成熟度图例

文档头部的“证据成熟度”是“本指南方法或建议的支撑证据成熟度”的机器可读简称。四个标签只描述逆向工程方法或建议的支撑证据成熟度，不描述目标产品主张的真假。目标产品主张使用主张状态、置信度和证据引用表达可信程度。

| 标签 | 在本指南中的含义 |
| --- | --- |
| `cross-project-validated` | 方法或建议已由至少两个相互独立的项目验证，可申请提炼为 Pattern，但仍需逐项审查方法证据与边界 |
| `project-validated` | 方法或建议已在一个真实项目验证，只能声称其在该项目边界内经受检验 |
| `industry-established` | 方法或建议有可追溯的行业标准、权威规范或稳定公开实践支持，仍需确认本地适用性 |
| `proposed` | 方法或建议尚待验证，必须明确标为候选做法，不能冒充已验证方法 |

## 当前范围

当前版本建立指南入口、治理规则、受众分流和证据成熟度，并纳入目标与范围、安全边界、证据模型、统一术语、端到端工作流、产品与业务建模、运行时实验、覆盖/质量/冻结和人机协作九项核心模块，黑盒、灰盒、白盒三条访问轨道，Delphi 桌面、Web 产品、Java 后端、.NET 后端和数据/消息/基础设施技术栈指南，包含 13 份人工可读记录模板、8 份 Draft 2020-12 JSON Schema、14 份正反样例、记录 CLI 和指南验证器的完整操作工具箱，以及一日分诊、一周评估和完整项目三套运行配置。它适用于从桌面端、Web、移动端到服务端和数据库的跨技术栈产品逆向，也适用于仅能静态阅读的遗留系统。后续模块必须引用这些基础契约；未纳入导航的内容不应被视为本指南的已发布模块。

不在当前范围内：绕过访问控制、获取未授权数据、替代法律或合规审查，以及仅凭静态文本声称运行时行为已经成立。

## 安全边界

- 只分析已获授权的系统、代码、账号、环境和数据，遵守组织的数据分级与保留规则。
- 优先使用脱敏样本和最小权限；不得把密钥、令牌、个人信息、客户数据或本机绝对用户目录写入仓库。
- 运行遗留系统、迁移数据或调用外部服务前，明确副作用、隔离环境和恢复方案；不在生产环境做破坏性探测。
- 将事实观察、源码解释和推断分开记录。无法复现的行为不能标为 `runtime-confirmed`，应调整主张状态或置信度并注明缺口。
- AI Agent 可以协助检索、关联和起草，但证据归属、风险接受和最终发布由人类负责人复核。

## 访问轨道导航

访问轨道按当前已获授权且能绑定身份的最强证据面选择，不表示项目等级，也不产生平行的主张状态。一个项目可以从黑盒开始再安全升级；新证据沿用同一对象和追踪关系，旧观察保持可寻址。

| 轨道 | 使用时机 |
| --- | --- |
| [黑盒访问轨道](access-tracks/black-box.md) | 只有公开信息和合法账号时，系统覆盖角色/套餐/地区/设备、页面状态与安全可观察路径 |
| [灰盒访问轨道](access-tracks/gray-box.md) | 获准读取包、配置、日志、API、只读数据、部署元数据、二进制或部分源码时，补强结构证据并显式保留静态上限 |
| [白盒访问轨道](access-tracks/white-box.md) | 获准使用完整源码与构建/测试/部署材料时，从入口追踪配置、事务、持久化和异步作用，并以部署身份与运行证据校准 |

三条轨道都必须先通过[授权、隐私与安全](core/authorization-privacy-and-safety.md)的 G0，并使用[证据与置信度](core/evidence-and-confidence.md)的证据项、主张和类型化追踪链接。访问增加时新建证据和关系，不原地把静态或可见观察改写成运行确认。

## 导航与发布顺序

**本节说明：** 证据成熟度：`proposed`。本节的阅读与执行顺序是当前建议，后续应根据真实项目证据调整并提升成熟度。

阅读顺序用于建立共同语言，执行顺序用于控制证据采集和阶段门禁。阅读某份文档不表示对应阶段已通过，也不授权任何采集或运行。

### 阅读顺序

1. 先阅读[目标、范围与完成定义](core/goals-scope-and-completion.md)，理解决策目的、八个范围维度和完成门槛。
2. 再阅读[授权、隐私与安全](core/authorization-privacy-and-safety.md)、[证据与置信度](core/evidence-and-confidence.md)和[术语表](glossary.md)，统一 G0、证据状态、置信度、对象与链接语义。这四份文档共同构成执行前的基础契约。
3. 基础契约理解一致后，根据当前授权选择[黑盒](access-tracks/black-box.md)、[灰盒](access-tracks/gray-box.md)或[白盒](access-tracks/white-box.md)访问轨道；再阅读[人机协作](core/human-agent-collaboration.md)并用任务包固定决策权、输入身份、输出和停止条件，随后阅读[端到端工作流](core/end-to-end-workflow.md)的十个阶段、回退规则和停止条件。
4. 在准备产品地图和 Phase 2 产物前阅读[产品与业务建模](core/product-and-business-modeling.md)；执行 Phase 5 前阅读[运行时实验](core/runtime-experiments.md)，进入 Phase 7–8 前阅读[覆盖、质量与冻结](core/coverage-quality-and-freeze.md)。这些模块按场景反复查阅，不是十阶段结束后的附加写作步骤。

### 执行顺序

1. **授权先行**：进入工作流后必须先完成 Phase 0，之后才可采集任何证据；阅读指南、编写未接触目标资产的任务草案不算证据采集。
2. **建立基线**：Phase 1 固定版本、配置和范围分母，Phase 2 从角色和产品表面建立产品地图，Phase 3 再定位技术资产。
3. **取证与建模并行演进**：Phase 4 建立纵向证据链，Phase 5 按运行时实验协议执行获准实验或受治理的静态替代验证。产品与业务建模从 Phase 2 开始迭代，并在 Phase 6 综合，而不是等十个阶段全部结束后再开始。
4. **审计、冻结与学习**：Phase 7 执行 G6，用九类分母和风险队列审计完整性与冲突；Phase 8 执行 G7，以确定性生成和冻结输入按主要目的映射交付。Phase 9 只基于可验证冻结基线做增量校准，并把受影响门禁恢复为 `pending` 后定向重验；全过程由任务包和人工决策权约束。

当前入口、治理基线和九项核心模块纳入仓库验证。新增模块发布时，应加入本节导航并复用同一证据标签，不得另建平行成熟度体系。

## 验证

在仓库根目录运行唯一的指南结构验证命令：

```bash
python3 tools/validate_product_reverse_engineering_guide.py
```

该命令检查指南入口、全部 Markdown 页面的页面级治理声明、九项核心模块和三条访问轨道、已发布技术栈指南、工具箱全量索引与本地链接闭包、模板/Schema/正反样例、三套运行配置及案例研究的治理契约是否齐全。对案例研究，它还检查章节结构、`source:*` 闭包与 Git blob OID manifest、计数、Phase、日期绑定、方法成熟度和脱敏边界；这些结构检查不证明指南中的技术结论、模板内容或案例产品主张已经在项目中验证。
