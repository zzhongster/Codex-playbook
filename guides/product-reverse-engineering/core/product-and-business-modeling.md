# 产品与业务建模

**证据成熟度：`proposed`**

**适用范围：** 适用于把已获授权产品的界面、运行、代码、数据、文档和领域证据综合为可追溯的产品与业务模型；不适用于仅凭文件名、表结构或行业常识断言目标产品行为，也不允许把历史观察静默升级为重写需求、竞品能力等价或战略结论。

建模的目标是解释“谁在什么边界内，经过哪些状态和规则，得到什么业务结果”，并让每个结论能够回到[证据与置信度](evidence-and-confidence.md)定义的证据项、主张状态和置信度。模型不是对源码目录的另一种排版，也不是理想产品设计；观察、推断、领域确认与目标决策必须保持可区分。

## 产品地图先行

先建立“角色—目标—产品表面—旅程—能力”的产品地图，再写任何逐文件叙述。文件、类、表和服务只能作为能力与行为的实现证据；若先按目录写说明，容易把技术分层误当产品边界，并遗漏横跨多个模块的用户结果。

产品地图至少记录稳定 ID、角色、目标、入口、可见条件、前置状态、预期结果、候选能力、关键路径、适用版本和证据。未知关系标为候选或缺口，不用空白表达“不存在”。

| 建图顺序 | 核心问题 | 主要输出 |
| --- | --- | --- |
| 1. 角色与目标 | 谁要完成什么结果，承担什么责任？ | 角色、服务身份、职责和目标清单 |
| 2. 产品表面 | 角色从哪里接触产品，在什么条件下可见？ | 页面、命令、API、报表、任务和通知目录 |
| 3. 旅程与路径 | 从前置状态到结果有哪些正常与异常路径？ | 场景矩阵、用户旅程和交接点 |
| 4. 能力与规则 | 产品通过什么业务能力、决策与约束产生结果？ | 能力地图、状态机、规则和语义词典 |
| 5. 技术追踪 | 哪些代码、服务、数据和异步作用支持上述行为？ | 类型化追踪链接与证据缺口 |

## 能力模型

能力以“参与者获得的业务结果”命名，而不是以菜单、团队或代码包命名。每项能力记录稳定 ID、参与者、触发、输入、结果、包含与排除边界、关键场景、规则、依赖能力、产品表面、责任人、版本和证据。

先画能力树或能力网络，再把多个入口、人工步骤和技术资产连接到能力。一个资产可以支持多个能力，一个能力也可以跨越多个资产；因此资产存在不证明能力可用，入口同名也不证明能力等价。

| 字段 | 建模要求 |
| --- | --- |
| 能力陈述 | 使用“为某参与者实现某结果”的句式，避免技术实现词 |
| 成功标准 | 给出可观察结果、业务边界和不算成功的情况 |
| 场景覆盖 | 关联正常、负向、逆向、重试、部分成功、批量和权限路径 |
| 证据与状态 | 链接支持和反驳证据，标明适用版本、主张状态和置信度 |

## 角色模型

角色描述责任、目标和被授予的业务权限；账号描述某次身份实例，两者不能互换。模型应覆盖操作人员、审批者、管理员、审计者、外部参与者、服务身份和代理关系，并标明职责分离、继承、临时授权及撤销条件。

同一人员在不同组织、租户、时间或流程阶段可能承担不同角色。角色记录至少包含稳定 ID、身份来源、责任、可操作资源、可见范围、禁止动作、授权者、有效期和证据；显示名称只作为别名。

| 关系 | 需要回答的问题 |
| --- | --- |
| 承担 | 哪个身份在何种上下文承担该角色？ |
| 授予 | 谁授予哪些动作和数据范围，何时生效或失效？ |
| 代理 | 代理人能否继承全部权限，行为归属记录给谁？ |
| 分离 | 哪些角色不能由同一主体同时承担，如何强制？ |

## 用户旅程

用户旅程从业务前置状态开始，到可核对的结果或终止状态结束，包含人工交接、外部系统和后台处理。每条旅程记录角色、目标、入口、步骤、决策点、状态、可见反馈、数据与异步副作用、耗时边界、退出条件和证据。

路径矩阵必须覆盖下列类型；“没有观察到”只表示证据缺口，不表示产品没有该路径。

| 路径 | 必须建模的内容 |
| --- | --- |
| 正常路径 | 有效输入如何到达成功状态，成功对角色意味着什么 |
| 负向路径 | 无效输入、前置条件不满足和业务拒绝如何呈现且不产生哪些副作用 |
| 逆向路径 | 撤销、退回、冲销、退款或反记如何关联原动作并恢复不变量 |
| 重试路径 | 谁可以重试，幂等键、次数、退避、终止条件和重复副作用如何处理 |
| 部分成功路径 | 子步骤成功与失败如何分界、呈现、补偿和继续 |
| 批量路径 | 单项与整批的原子性、排序、限额、汇总和逐项结果 |
| 权限路径 | 无权限、权限过期、范围不足和职责冲突分别在哪一层阻断 |

## 交互模型

交互是角色或外部系统通过一个产品表面发起动作并接收反馈的最小可观察单元。它可以是点击、键盘操作、API 调用、导入、批任务、通知确认或人工交接，不能只用控件事件名称代表完整交互。

每条交互记录前置状态、角色与身份、入口、输入、动作、即时反馈、延迟反馈、同步写入、异步副作用、后置状态、可撤销性、错误呈现和证据。用户看到“成功”时仍需核对事务、消息和外部系统；后台完成但用户未获反馈也应单独建模。

| 层面 | 追踪重点 |
| --- | --- |
| 用户可见 | 可用性、默认值、确认、错误、进度、最终结果和可访问性 |
| 服务边界 | 请求身份、校验、幂等、超时、响应和错误映射 |
| 数据与异步 | 事务提交、派生数据、事件、通知、调度和补偿 |

## 状态机

状态机描述业务对象在明确事件下如何转换，而不是枚举数据库状态码。每个状态和转换使用稳定 ID，并记录源状态、事件、目标状态、守卫条件、副作用、原子性、触发角色、失败结果、补偿、时间边界和证据。

守卫条件回答“在何种版本、权限、数据和并发条件下允许转换”；副作用回答“转换提交后还会更新、发布、通知或派生什么”。守卫失败必须与执行失败分开，副作用部分完成必须进入错误与补偿模型。

| 源状态 | 事件 | 守卫条件 | 目标状态 | 副作用 | 失败或补偿 |
| --- | --- | --- | --- | --- | --- |
| 状态候选 A | 业务事件 | 权限、版本、字段、额度或时间条件 | 状态候选 B | 写入、事件、通知或汇总 | 保持原状态、回滚、重试或补偿候选 |

审查时显式寻找不可达状态、终态、循环、并发转换、回退边和绕过路径。单个 `status` 字段、按钮禁用或分支语句只能支持状态候选；需要与交互、数据变化或领域证据共同确认业务语义。

## 业务规则

每条规则建立独立记录，至少包含：稳定 ID、自然语言、公式或决策表、正反例、适用边界、证据、主张状态、置信度、所有者、版本、优先级以及与其他规则的冲突关系。规则陈述应可判定，避免“通常”“合理”“按需”等没有边界的表述。

自然语言说明业务意图和触发上下文；公式或决策表精确表达计算和分支；正反例暴露边界与例外；适用边界限定版本、角色、租户、配置、币种和时间；证据同时包含支持项与反驳项。只有代码命名或行业惯例时，规则保持候选状态。

| 规则记录字段 | 最低内容 |
| --- | --- |
| 自然语言 | 在给定条件下，系统允许、拒绝、计算或触发什么 |
| 公式或决策表 | 运算顺序、条件组合、默认分支和未知值处理 |
| 正反例 | 一个满足例、一个拒绝或边界例及预期结果 |
| 适用边界 | 版本、角色、配置、数据域、时间窗和例外 |
| 证据 | 来源身份、定位、支持或反驳关系和取证时间 |

## 决策表

决策表用于条件组合、优先级或例外多于一维的规则。先枚举条件域与未知值，再列动作、命中策略、默认分支、冲突处理和不可能组合；不能把未观察组合填成“否”。

| 条件 A | 条件 B | 权限上下文 | 动作 | 规则优先级 | 证据/状态 |
| --- | --- | --- | --- | --- | --- |
| 真 | 真 | 允许 | 动作候选 A | 明确值 | 对应证据与当前主张状态 |
| 真 | 假 | 允许 | 动作候选 B | 明确值 | 对应证据与当前主张状态 |
| 未知 | 任意 | 任意 | 保留未知，不推定动作 | 不适用 | 验证缺口 |

用正常、边界、冲突和未知组合回放决策表，并与代码分支、运行结果和领域陈述交叉核对。多个规则同时命中时，记录实际优先级或将其标为冲突，不按文档顺序臆测。

## 公式

公式模型记录输入、输出、量纲、币种或单位、精度、舍入方式、舍入时点、运算顺序、空值、溢出、负数、阈值、累计窗口和适用版本。文本相同但舍入阶段不同的公式是不同规则。

每个公式至少附一个正常例、一个边界或反例，以及中间结果。运行样本用于确认实现行为，领域确认用于判断业务意图；二者冲突时保留两个主张并进入冲突处理。

```text
结果候选 = Round(输入数量 × 单价, 指定精度与舍入方式)
```

上式只是记录结构示例，不是任何目标产品的事实。真实模型必须给出单位、币种、符号、税基、折扣顺序、每行或汇总舍入，以及支持该版本的证据。

## 权限模型

权限模型以“主体—角色—资源—动作—条件—范围—效果”表达，并记录授权来源、优先级、继承、显式拒绝、有效期和审计归属。界面隐藏、客户端禁用、服务拒绝、数据行过滤和字段掩码是不同控制点，不能互相代替。

同时验证人员与服务身份、跨租户边界、代理、批量操作、导出、后台任务和逆向路径。拒绝结果需说明发生在哪一层、是否产生数据或异步副作用，以及用户能看到多少信息。

| 维度 | 关键问题 |
| --- | --- |
| 动作权限 | 能否查看、创建、修改、批准、撤销、导出或管理？ |
| 数据范围 | 限定组织、租户、部门、所有者、记录、字段还是时间窗？ |
| 条件与优先级 | 角色叠加、显式拒绝、临时授权和职责分离如何决胜？ |
| 执行位置 | 客户端、服务端、数据层或异步消费者分别如何强制？ |

## 关键业务语义

语义记录必须说明业务含义、技术表示、边界、变换、生命周期和证据。相同字段类型不代表相同语义；跨模块共享值也不能默认共享身份、时间基准或删除规则。

每个语义项关联使用它的能力、规则、状态和数据对象，并明确未知、空值、默认值、历史版本和迁移行为。

### 金额语义

记录币种、含税或未税、借贷或收支方向、精度、舍入模式、舍入时点、汇率来源、汇率有效时间和负数含义。核对行级与汇总级差异、退款或冲销符号，以及跨币种重估是否改写历史金额。

金额字段的存储精度只是证据之一；界面显示、服务计算、数据库汇总、报表和对账必须在相同场景下交叉验证。

### 数量语义

记录计量单位、基本单位与辅助单位、换算精度、正负方向、可分割性、批次或序列约束、预留、在途和可用口径。区分物理数量、账面数量和派生数量。

退货、拆装、部分履约和批量导入可能使用不同单位与舍入阶段，必须通过例子和状态变化说明守恒边界。

### 时间语义

记录业务日期、记账日期、创建时间、提交时间、生效时间、结算周期、时区、日界线、精度和时钟来源。区分事件发生时间、系统接收时间和处理完成时间。

验证夏令时、跨日、月底、迟到事件、回溯生效与关闭期间；界面日期不自动代表数据库或外部系统使用的时间基准。

### 身份语义

记录业务对象 ID、技术主键、外部 ID、自然键、别名、版本和合并或拆分关系。名称可变且可能重复，不能作为跨系统唯一身份。

确认身份由谁分配、在何范围唯一、重建或导入时是否保持，以及历史记录如何指向被合并或停用的对象。

### 租户语义

记录租户、组织、账套、法人或工作区边界，说明身份、配置、数据、缓存、任务和密钥在哪一级隔离。共享基础设施不等于共享业务数据。

跨租户查询、模板、管理员支持、合并报表和迁移工具需要单独授权与证据；任何偶然可见数据都按越界路径处理。

### 可见性语义

记录对象对哪些角色、渠道、状态和时间窗可见，以及隐藏、掩码、过滤、延迟发布和撤回的差别。不可见不等于不存在，也不等于无权直接访问底层接口。

分别核对列表、详情、搜索、导出、报表、通知和 API，防止一个表面的过滤被误认为全局权限规则。

### 历史语义

记录修改前值、版本链、审计事件、有效时间与记录时间、重算和更正方式。区分快照、事件、当前值覆盖和双时间语义。

确认历史是否可见、可查询、可重放或仅供审计，以及规则版本变化后旧交易按旧规则保留还是重新计算。

### 删除语义

区分物理删除、软删除、归档、停用、作废、撤销、匿名化和法定保留。记录谁可发起、等待期、级联、恢复、搜索可见性、审计和外部副本处置。

删除按钮或字段标记不能单独证明数据已清除；数据库、缓存、索引、附件、消息、备份和下游系统需按批准边界分别核对。

## 错误与补偿

错误模型区分输入校验、业务拒绝、权限拒绝、并发冲突、依赖失败、超时、资源限制和未知故障，并记录用户反馈、机器错误、可重试性、数据状态、异步状态与审计事件。不要用一个通用错误码吞掉业务差异。

补偿模型说明事务边界、已完成子步骤、幂等身份、重试所有者、次数与退避、去重窗口、补偿动作、人工介入和最终一致性门槛。部分成功和批量操作必须同时给出逐项结果与整体结果；重试不能覆盖首个失败证据。

| 失败点 | 已提交内容 | 用户可见结果 | 重试与幂等 | 补偿与责任人 | 最终核对 |
| --- | --- | --- | --- | --- | --- |
| 候选步骤 | 数据、事件或外发候选 | 明确成功、失败或处理中 | 键、窗口、上限和终止条件 | 自动、人工或不可补偿 | 状态、不变量与通知 |

## 跨模块不变量

不变量是在多个能力、模块、数据对象或异步阶段之间必须持续成立的约束。每条记录包含稳定 ID、业务理由、参与对象、前置与后置条件、守恒或唯一性表达、事务和并发边界、例外、检测点、修复责任、适用版本与证据。

常见候选包括身份唯一且引用可追踪、金额或数量在批准边界内守恒、状态转换与流水一致、权限与租户隔离不因异步处理失效、逆向动作可关联原业务、历史记录不可被当前值无痕覆盖。它们只是候选类别，必须用目标产品证据逐条确认。

| 不变量视角 | 跨模块审查问题 |
| --- | --- |
| 身份与引用 | 同一业务对象跨界后如何保持身份，合并、拆分和删除如何传播？ |
| 金额与数量 | 创建、履约、结算、退款或冲销后，在哪个边界守恒或允许差额？ |
| 状态与流水 | 汇总状态能否由明细和事件重建，部分成功如何表达？ |
| 权限与租户 | 后台任务、缓存、导出和集成是否保持原授权与隔离上下文？ |
| 历史与审计 | 更正、重算、补偿和迁移是否保留原事实及责任归属？ |

不变量至少用一个正常场景和一个破坏尝试验证，并关联到监测或验收。若旧实现违反领域期望，应分别保留“历史行为”和“目标约束”主张，不用修复意图改写观察。

## 重写输出

重写输出服务于目标系统取舍。**观察不会自动成为需求**：每条旧产品行为先保留证据主张，再由有权限的产品或领域负责人选择保留、纠正、有意舍弃或继续研究，并说明用户影响、风险、迁移策略和验收标准。

重写记录至少建立三种不同对象：旧行为主张 `OBS-*`、目标需求 `REQ-*`、重写决定 `DEC-RW-*`。决定用类型化链接引用观察和需求；目标需求不能继承旧行为的 `runtime-confirmed` 状态，也不能因旧代码存在而默认优先。

| 重写字段 | 要求 |
| --- | --- |
| 旧行为 | 限定版本、角色、场景、状态、置信度和证据 |
| 目标选择 | 保留、纠正、有意舍弃或继续研究 |
| 决策理由 | 用户价值、风险、法规、迁移和兼容性权衡 |
| 验收 | 可执行场景、期望结果、容差和决定人 |

## 竞品输出

竞品输出服务于可比能力、旅程和定位问题。**观察不会自动成为战略判断**：公开或另行获准证据只支持其版本、套餐、角色、地区、配置和观察时间内的事实；功能名称相似不等于能力、质量或市场价值等价。

竞品记录分别建立观察主张 `OBS-COMP-*`、比较解释 `HYP-COMP-*` 和战略决定 `DEC-COMP-*`。解释必须列出替代解释和证据缺口，战略决定由相应负责人作出；不得为了补齐矩阵越过授权、付费或访问控制边界。

| 竞品字段 | 要求 |
| --- | --- |
| 可比边界 | 版本、套餐、角色、地区、配置、时间和来源权限 |
| 可观察差异 | 产品表面、旅程、结果和限制，不夹带价值判断 |
| 解释假设 | 可能原因、替代解释、反证和置信度 |
| 战略问题 | 该差异是否重要、对谁重要、由谁决定和何时复核 |

## 输出隔离门禁

发布前分别抽查重写与竞品输出：事实主张是否仍链接原证据，需求或战略判断是否拥有独立决定人，历史缺陷是否被明确选择，比较是否使用一致边界。一个观察可以被两类输出引用，但必须有两条不同类型的决策链接，不能复制文本后丢失对象身份。

当证据冲突、比较边界不一致或决定人缺失时，保留观察并停止发布对应需求或战略结论。模型完整度不构成决策授权，机器校验通过也不提高产品主张的置信度。
