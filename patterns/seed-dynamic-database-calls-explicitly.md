# Pattern: Seed dynamic database calls explicitly

## 一句话结论

当遗留客户端通过字符串变量、配置表或中间件包装器动态选择 SQL、存储过程和表时，静态解析器无法可靠生成数据库边；应增加经过限定和审查的显式数据库 seed，并把“对象存在”和“业务语义确认”分开。

## 典型缺口

静态解析通常能识别：

- 源码中的直接 SQL 文本；
- 固定字符串形式的过程名；
- 数据组件中静态配置的表名。

但下列调用经常没有可靠图边：

- `OpenProcByName(variable)` 或 `ExecuteProc(calculatedName)`；
- 从数据库功能表加载后再调用的过程名；
- 由单据类型、版本或账套配置拼装的对象名；
- 中间件内部二次分派，客户端只看到通用方法。

## 实现模式

1. 先保留静态提取结果，不能为了补边而修改解析器输出或伪造直接调用。
2. 显式 seed 使用完全限定身份：调用点、模块、数据库对象类型、对象名；字段级关系还需字段名。
3. 每条 seed 必须携带可定位证据、关系类型、置信度、状态和验证方法。
4. 加载器要求 seed 恰好解析到一个已登记数据库对象；零匹配、多匹配和类型不符都失败。
5. “对象/字段存在”只允许证明结构关系；特殊值、方向、金额含义、累计逻辑等仍需源码、数据库定义或运行证据。
6. 将 seed 生成的边单独标记，便于后续真实运行追踪对其确认、冲突或替代。
7. 父级守恒式引用 seed 边时，必须保留其证据状态和未来验证方法，不能自动升级为 confirmed。

## Seed 最小字段

| 字段 | 作用 |
|---|---|
| `source_id` | 已登记的调用点、函数或业务记录 |
| `database_kind` | table、field、procedure、view 等封闭类型 |
| `database_name` | 规范化对象名 |
| `field_name` | 字段关系时必填 |
| `relation` | read、write、invoke、project 等封闭关系 |
| `status` / `confidence` | 区分确认、部分、冲突与未知 |
| `evidence` | 相对路径、行范围和 SHA-256 |
| `validation_method` | 未确认语义的精确后续验证方式 |

## 常见错误

- 看到表名相似就自动连边。
- 用 seed 直接声明金额方向、特殊值或过账时点。
- seed 引用短名称，实际解析到多个历史版本对象。
- 运行验证后覆盖 seed，导致原推断过程不可追踪。
- 动态调用没有边时，把它当成“没有数据库副作用”。

## 验证清单

- 动态调用缺边时会进入明确诊断，而不是静默遗漏。
- 每条 seed 精确解析一次，且证据路径与哈希有效。
- 结构存在、调用关系和业务语义使用不同记录类型。
- 不支持的语义仍为 P2，并带可执行验证方法。
- 删除 seed 后，测试能准确暴露缺失的数据库关系。

## 证据范围与晋级条件

当前证据来自同一 ERP 中多个动态菜单、通用数据模块和跨业务单据调用。下一步应在另一个使用 ORM 反射、配置驱动 SQL 或 RPC 路由的项目中验证，以确认该模式不依赖 Delphi/MIDAS 的具体实现。
