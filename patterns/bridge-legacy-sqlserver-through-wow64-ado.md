# Pattern: Bridge legacy SQL Server through WOW64 ADO

## 一句话结论

在只能使用 SQL Server 2000/MSDE 与旧版 `SQLOLEDB` 的 Windows 实验室中，用 64 位控制器完成安全检查，再显式切换到 `SysWOW64` 的 32 位 Windows PowerShell 执行 ADO 数据库操作；不要把 64 位进程中的 provider 失败误判为数据库不可用。

## 适用场景

- 目标是 SQL Server 2000、MSDE 或只能由 32 位 OLE DB provider 访问的旧实例。
- 宿主是 64 位 Windows，但旧 Delphi 程序及其数据库驱动来自 32 位时代。
- 自动化任务需要读取目录、备份、恢复或校验一次性克隆，又不能升级原产品的数据库依赖。

## 已观察到的对照

- 同一主机、同一本地数据库和同一集成身份下，64 位 PowerShell 中的旧 provider 连接失败。
- 改由 `SysWOW64\WindowsPowerShell\v1.0\powershell.exe` 执行相同 ADO 连接后成功，并可完成备份、恢复、聚合指纹及 DBCC。
- 这说明失败边界位于进程位数/provider 组合，而不是账套不存在或 SQL Server 未运行。

## 实现模式

1. 控制器先检查数据库名只能是简单 SQL 标识符，源库与克隆库必须不同。
2. 若当前进程为 64 位，显式调用 `SysWOW64` 下的 PowerShell，并原样转发经过验证的参数。
3. 32 位 payload 使用集成身份和本地连接，不在脚本中写入用户名、密码或连接秘密。
4. 打开连接后立即执行 `SELECT DB_NAME()`，每次写入前再次断言当前目标是唯一克隆库而非源库。
5. 把解析、脚本 SHA-256、源库指纹、克隆基线、反向清理、DBCC 和克隆删除设为独立失败门禁。
6. 控制器透传 32 位子进程退出码；不能只看“脚本已启动”或某一条成功输出。

## 常见误判

- “64 位 ADO 连不上，所以数据库坏了”：应先用同机 32 位 provider 做受控对照。
- “安装新驱动即可”：可能改变遗留产品真实运行条件，破坏兼容实验的证据价值。
- “连接成功就可以写”：仍需逐次断言数据库目标，并证明源库前后差异为零。
- “PowerShell 路径中的 System32 表示 32 位”：在 64 位进程中并非如此，32 位入口是 `SysWOW64`。

## 验证清单

- 64 位入口会确定性地切换到 32 位进程。
- Windows PowerShell 5.1 能解析全部执行依赖，且文件哈希匹配已提交清单。
- 每个数据库写入前都有精确的克隆目标断言。
- 源库最终指纹与基线一致，克隆写入可见、反向清理后差异为零。
- DBCC 通过，临时对象为零，克隆已删除。

## 证据范围与晋级条件

当前证据来自一个 Delphi 5/SQL Server 2000 遗留 ERP 的多个独立校准阶段。若在第二个旧版 SQL Server 产品中复现，应补充其 provider、Windows 版本和失败/成功对照；若现代 x64 provider 可用，应优先使用受支持的 64 位链路。
