# 反模式：把数据库聚合探针当成旧界面行为证明

## 一句话结论

`COUNT_BIG`、`CHECKSUM_AGG`、表存在性和 DBCC 只能证明数据库可达、克隆安全及聚合状态可比较，不能证明旧界面的按钮、筛选、穿透、状态迁移、报表计算或打印导出已经运行；这些场景必须保持 `unsupported`，直到旧客户端被精确绑定到一次性克隆并实际回放。

## 场景

逆向 Delphi/SQL Server 遗留 ERP 时，静态分析已经找到窗体处理函数、存储过程、数据表和字段。Windows 实验室也能通过 32 位 ADO 访问账套，并在一次性克隆中执行聚合查询和可逆哨兵写入。

## 失败做法

- 看到相关表存在，就把“按钮可用”标成运行确认。
- 聚合查询成功后，推断筛选条件、默认值、余额方向和穿透目标均正确。
- 根据第三方网格组件支持排序/隐藏列，宣称具体业务窗体已启用这些交互。
- 用克隆安全门禁通过代替业务场景回放，把静态证据升级为动态事实。

## 为什么错误

数据库探针绕过了旧客户端中的权限、控件状态、参数拼装、确认框、异常反馈、事务顺序、刷新、焦点和输出渲染。它验证的是基础设施与数据边界，不是产品行为。若把两者合并，生成文档会制造“看起来完整、实际未经运行”的虚假确定性。

## 正确做法

1. 把运行阶段分为安全阶段、聚合可达阶段和业务 UI 阶段，使用封闭的阶段词汇。
2. 安全阶段验证源账套前后指纹为零、源/克隆基线相同、写入只发生在 `GJP6_` 克隆、逆操作恢复基线、DBCC 通过、临时对象为零且克隆已删除。
3. 聚合探针只把对应的“表集合可达/只读聚合查询”标成 `passed`。
4. 需要按钮、菜单、穿透、状态迁移、计算或输出的场景，在没有克隆绑定旧 UI 时一律标成 `unsupported`。
5. 每个 `unsupported` 记录必须带精确的未来验证方法，包括入口、哨兵、预期聚合差异、逆操作和清理条件。
6. 父阶段只能汇总子阶段的安全结论，不能把多个单模块静态事实拼成“跨模块联合动作已确认”。

## 已验证效果

在同一遗留 ERP 的账簿报表与出纳银行两轮独立校准中：

- 所有源库、克隆基线、逆操作、DBCC 和克隆删除安全门禁通过；
- 只把实际执行的聚合账簿/日记账查询升级为运行确认；
- 分别保留 7 个依赖旧 UI 的场景为 `unsupported`；
- 跨模块父阶段继续保留 8 个联合 UI 场景为 P2，同时父子 P0/P1 保持为 0。

这使“安全可执行”“数据可达”“产品行为已观察”成为三个独立、可审计的结论。

## 验证清单

- 每个 `passed` 业务阶段都有实际执行证据，而不是表存在或组件能力。
- 运行引用不包含地址、身份、凭据、截图、原始日志或业务明细行。
- 未运行场景没有从 `unsupported` 静默升级。
- 父阶段保留所有未支持联合场景及精确回放方法。
- 安全门禁失败会阻断发布，但安全门禁通过不会自动确认 UI 行为。
