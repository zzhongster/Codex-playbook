# 切换 Agent 后继续加载旧技能副本

## 一句话结论

仓库代码已更新、旧 Agent 的技能软链已更新，都不能证明新 Agent 实际加载的技能已更新；接手前要核对技能发现路径、链接终点和可执行入口。

## 场景

2026-10-08，一次报告工具项目从 Claude 转到 Codex。三个报告技能已在仓库完成改造：先取得报告计划，再调用共用套件生成文件。Claude 的对应技能链接到仓库主目录，Codex 可用技能目录中却还有三份独立的旧副本。

这是单项目观察，尚未跨项目复现。它与模型能否读取仓库无关：模型能看到新代码，同时仍可能按技能目录中的旧流程操作。

## 失败表现

- 三份 Codex 共享目录中的 `SKILL.md` 与仓库当前版本全部不同。
- 旧版三份文件都没有 `plan_report`、`_report_kit`、`scripts/build.py`；仓库新版三份都含有这些入口。
- 旧目录中还有仓库对象库找不到的模板和说明。不能把“落后于仓库”直接等同于“可删除”。

此次在执行新报告之前发现了配置漂移，没有把它描述为已经发生的错误报告交付。

## 根因

技能至少有三个不同身份：仓库中的源文件、宿主发现到的安装路径、当前会话已加载的内容。复制安装会随时间漂移；软链只解决它所连接的那一个安装位置。换宿主不会自动继承另一个宿主的链接。

此外，共用套件可能不在单个技能目录内。只复制 `SKILL.md`，或只复制入口目录，即便说明文字是新版，也可能让入口找不到相邻的共用库。

## 正确做法

1. 以当前宿主暴露的技能清单为起点，记录实际读取的 `SKILL.md` 路径，不凭另一个宿主的配置推断。
2. 核对是否为链接、最终指向哪里、源文件内容哈希是否相同，以及入口依赖的相邻资源。
3. 更新前完整备份旧目录，保留本机独有文件和清单；备份放在技能发现目录之外，避免新旧版本一起被发现。
4. 本机开发场景可链接到稳定仓库目录。入口若通过 `Path(__file__).resolve()` 查找相邻库，应从实际安装路径执行一次，验证软链下的依赖定位。
5. 已运行会话可能还保留旧说明；本轮显式读取新源文件，后续新会话再核对发现清单。不要宣称所有宿主都支持热刷新。
6. 使用实际解释器从安装入口执行，记录退出码。`--help` 只证明启动与依赖定位；完整产物验收仍须另跑。

## 验证清单

本次实际完成的检查：

| 检查 | 结果 |
|---|---|
| 三个旧报告技能与仓库一致 | 0 / 3 |
| 更新后六个相关技能链接到预期源目录 | 6 / 6 |
| 旧目录与独有模板保留 | 已完整备份，附每个文件的 SHA-256 清单 |
| 系统 Python 从三个安装入口运行 `--help` | 3 / 3 返回 0 |
| 系统 Python 3.9 从三个入口生成离线合成样例 | Excel / Word / HTML 均返回 0；只是兼容性验证，未替代真实业务报告验收 |
| 所有宿主自动重载技能 | 未验证，不作为本次结论 |

## 适用范围

适用于跨 Agent 迁移、同名技能多处安装、插件升级后仍保留手工副本，以及依赖相邻共用库的技能。软链是本机开发方案；部署到其他机器时应使用包含依赖的完整安装包，并在那里重新验证入口。
