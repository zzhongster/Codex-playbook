# 反模式：把外部视频“可导入、可恢复”当成“原生页面可用”

## 一句话结论

版本文件存在、恢复接口成功和原生播放器可用是不同契约；外部视频必须有真实来源、完整恢复语义和实际页面播放证据，不能伪造原生模型执行记录来过门禁。

## 场景

2026-10-20，在固定 ArcReel 上游镜像上增加 LibTV 已有视频回传。保留原生 ProjectManager、VersionManager、鉴权和正式文件事务，通过独立适配层支持外部来源。

证据成熟度：`project-validated`。镜像 digest、上游提交、实现提交和证据文件哈希见本次清单。测试视频由已有占位图在本地编码，实际时长分别2秒和3秒，镜头计划时长为8秒。

## 失败表现

这是实际页面检查发现的故障：

1. 两段视频从云端下载后，哈希与原件相同，导入成为 v1/v2。
2. 原生历史接口标记版本可恢复。
3. 打开镜头时，却没有视频元素，播放器提示所选演示不可用。

根因不是“文件没传回来”或计划时长8秒：原生演示读模型在选版本时，只接受它认识的生成来源或手工上传来源，新增外部来源在探测真实时长之前就被拒绝。

另一个实施前源码核验发现的限制是：原有手工上传视频记录不能据此推断完整的历史恢复已经可用。只测图片回滚，也不能证明外部视频恢复。

## 根因

把几个独立边界合成“上传成功”：

| 边界 | 真正需要证明的事实 |
| --- | --- |
| 字节传输 | 下载文件与选定原件一致 |
| 正式导入 | 文件、版本、镜头关联和回执原子落库 |
| 版本恢复 | 旧文件与对应旧来源一起恢复，保留其他历史 |
| 演示读取 | 当前/历史选择被原生读模型识别，能够形成播放数据 |
| 页面播放 | 浏览器能解码并实际前进，切版刷新后读到正确版本 |
| 生成进度 | 该产物是否满足原生生成依据；不能由播放器可用反推 |

因此，接口200、文件存在、缩略图成功或 `restorable=true` 都不足以证明整条用户路径成立。

## 正确做法

### 保存可验证的外部来源

本次使用独立的外部来源类型，记录操作身份、真实远端结果引用、冻结输入快照、内容哈希和实际媒体探测值。已有测试上传没有生成任务或模型执行证据，这些字段保持空值，不从当前设置倒推历史生成依据。

恢复前重新验证 manifest、版本快照与文件哈希。当前版本还要核对当前文件和所选历史快照是否一致；损坏时拒绝展示和恢复，而不是悄悄回落到另一份同名文件。

### 在原生播放读模型做窄适配

- 对经过校验的外部版本，复用原生 raw presentation 分支，使用实际解码时长。
- 保留 `provenance='unavailable'` 与空的原生生成依据；不冒充供应商执行，不凭空生成字幕、配音或时间对齐。
- HTTP 演示、历史演示和原生下载使用同一个校验入口。
- 原有来源委托原实现，保留原有鉴权和错误语义。

本次页首完成数仍按原生生成依据计算，未把外部视频计入；这项限制与“能在镜头中播放、切版”分别记录。后续若要适配进度统计，应另外定义诚实的外部产物语义。

### 固定字节身份与版本选择

导入的哈希对象必须说清楚。会改变 MP4 容器布局的处理可能改变字节哈希；本次采用保留原字节的暂存路径，探测和缩略图读取不改写原文件。若产品确实要转码，应分别记录原件和派生文件的身份，不能沿用原件哈希。

恢复 v1 是选择已有版本，不是复制出 v3；再续传已归档 v2 也不能擅自把当前选择切回 v2。

## 验证清单

- [ ] 当前与历史版本的原生播放接口均可读，文件内容与预期版本一致。
- [ ] 损坏快照和当前文件身份不匹配时拒绝，不伪造来源补齐必填项。
- [ ] 实际页面出现视频元素，真实键盘/按钮触发播放，播放时间向前移动。
- [ ] 在历史页面选择 v1、点击切换、刷新、再播放，实际时长和文件哈希属于 v1。
- [ ] v2 历史仍在，恢复不增加版本。
- [ ] 重启后选择与映射保留，续传只返回原回执。
- [ ] 页面完成数、原生生成依据和外部播放能力分别说明。

本次实机 v2 播放时长3秒，浏览器播放就绪状态为4，播放时间已前进；切回 v1 并刷新后播放时长2秒。固定镜像的17项服务测试还覆盖当前/历史媒体地址、下载包、来源校验和损坏拒绝。

## 适用范围

适用于有独立版本、播放读模型和生成来源门禁的媒体工作台。本次不证明配音、口型、字幕、时间线导出、任意容器格式或其他上游版本兼容；没有将原生生成进度规则全面扩展到外部媒体。
