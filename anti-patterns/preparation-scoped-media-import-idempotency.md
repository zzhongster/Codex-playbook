# 反模式：把回传幂等身份绑在一次准备或聊天上

## 一句话结论

同一远端结果的回传身份要跨准备、聊天和进程重启保持稳定；先查接收端已提交的回执，再决定是否传文件，不能靠“上一次调用成功了没有”判断是否新建版本。

## 场景

2026-10-20，ArcReel 与 LibTV 的单人、多 Codex 视频制作工作流接线：本地已有图片交给云端，再把已有测试视频回传原镜头并保留版本。

证据成熟度：`project-validated`。本次只搬运已有文件，没有调用图片、视频、语音生成或付费导出；没有在第二个独立项目验证，暂不列为 Pattern。

## 失败表现

下列问题由实现审查定位，再以回归测试或实机操作验证修复；并非每一项都曾在生产环境造成重复版本。

| 错误设计 | 结果 | 修复后的证据 |
| --- | --- | --- |
| 回传键包含准备记录 ID，而准备键包含当前视频版本 | 成功导入改变当前版本；重新准备后，同一视频得到新键，可再次建版 | 实机“回传→重新准备→回传原节点”仍返回 v1，后来加入 v2 后总数仍为2 |
| 只在本地记录“已经导入” | 接收端提交后回执丢失，下一位 Codex 无法确认是否成功 | 接收端持久回执查询、服务重建后的回执恢复测试通过 |
| 下载缓存丢失后，用最新准备内容重建原操作的 manifest | 原操作 ID 未变，输入指纹却改变，破坏原操作语义 | 回归测试固定原 manifest；重新下载只核对原结果哈希 |
| 所有失败永远复用原 manifest | 已明确拒绝的输入冲突，即使重新准备也无法采用已有结果 | 已确认409后，明确确认新输入才允许创建新的采用尝试 |
| 上传完成回执丢失后，重新发整份文件 | 已完成的分片可能被重复上传，甚至对已关闭上传会话执行 PUT | 分片完成检查点先落盘；完成回执丢失测试验证不再上传分片 |

## 根因

把业务结果、准备快照、回传尝试和网络调用混成一个身份。准备可以更新，网络可以重试，结果已经落库这一事实却不能随之重置。

另一种相反错误，是把“幂等”理解成永远不能开始新的采用尝试：已确定没有提交的输入冲突，需要明确的新采用动作；未知是否提交则只能继续查原操作。

## 正确做法

### 分清三层身份

- **准备快照**：目标项目、剧本、镜头、绑定画布、输入指纹和预期当前版本。画布改变时不能复用旧画布的准备记录。
- **结果身份**：明确远端画布与节点、对应本地目标、已观察到的文件内容身份。已成功归档的结果不能因为重新准备而变成新结果。
- **操作身份**：原始不可变 manifest 与稳定操作 ID。网络重试、换聊天、重启和补下载都沿用它。

内容哈希证明文件字节，不能单独证明镜头归属；文件名、节点显示名和项目里“最新视频”也不能替代明确映射。

### 在接收端完成原子提交

在同一个原生版本写入事务中：

1. 查同一操作是否已有提交；有则返回原版本，不重新选择当前版本。
2. 校验目标镜头、冻结输入指纹和预期当前版本；变化时拒绝覆盖。
3. 校验下载文件的哈希、格式及可解码性。
4. 提交文件、版本元数据、镜头关联和可恢复回执；任一步失败都回滚相关正式写入。

本地账本用于协调，接收端正式版本记录用于确认是否已经落库；不能用客户端唯一键代替服务端幂等。

### 恢复时先判断事实

| 已知状态 | 下一步 |
| --- | --- |
| 已成功提交 | 返回原版本及当前实际选中的版本；二者可以不同 |
| 回执未知、超时或断网 | 查询原操作，原文件和原 manifest 保留，不换键 |
| 已确认因输入/当前版本变化而拒绝 | 重新准备，取得用户对采用已有结果的明确确认，再开始新的采用尝试 |
| 远端链接过期 | 重读原节点取得文件链接，不重新生成 |
| 原结果内容哈希变化 | 停止，不在原操作名下替换内容 |

确认字段必须严格校验为布尔值；字符串 `"false"` 不能因语言真值规则成为用户确认。

## 验证清单

- [ ] 初次并发导入同一操作只能建立一个版本。
- [ ] 重复调用、重新准备、进程重建和接收端重启后仍返回原回执。
- [ ] 原操作 ID 不允许更换来源、哈希或冻结输入。
- [ ] 删除本地下载缓存后，恢复仍使用原 manifest。
- [ ] 切回 v1 后重放已归档的 v2，只返回 v2 回执，当前仍为 v1。
- [ ] 输入冲突拒绝覆盖；确认采用流程与未知回执恢复流程分开。
- [ ] 上传完成回执丢失只重复完成确认，不重复上传分片。

## 适用范围

适用于拥有持久结果身份、可查询回执和原子版本写入入口的媒体导入或文件交付。供应商没有查询/幂等能力时，客户端账本不能自行保证远端 exactly-once。新付费生成的批准与收费语义未在本次验证。
