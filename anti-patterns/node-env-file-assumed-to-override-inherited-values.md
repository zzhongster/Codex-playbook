# 反模式：以为 Node 的 `--env-file` 会覆盖继承环境变量

## 一句话结论

用 `node --env-file=.env.local` 做模型连通性验证时，不能假定文件中的同名变量会覆盖父进程已导出的值；先清除目标变量，才能验证本地配置实际会被使用。

## 场景

一个 Web 应用通过 `.env.local` 保存兼容 OpenAI 接口的模型服务地址和 API Key。开发机的桌面工具进程同时继承了另一套同名模型环境变量。

## 失败表现

- 本地连通性脚本报告 Key 前缀或服务地址与 `.env.local` 不一致。
- 服务端请求被发送到错误的模型网关，出现鉴权或路径错误。
- 直接查看 `.env.local` 看起来正确，因此问题被误判为配置文件路径或模型供应商故障。

## 根因

在 Node.js 24.18 的实测环境中，`--env-file` 只补充不存在的变量，不会覆盖已经继承到 `process.env` 的同名变量。桌面工具、shell profile 或上层启动器预先导出的变量因此具有更高优先级。

## 正确做法

1. 诊断时只输出变量是否存在、长度或允许公开的 host；绝不输出 Key 本身。
2. 用显式清除后的最小命令验证，例如：

   ```sh
   env -u MODEL_API_KEY -u MODEL_BASE_URL \
     node --env-file=.env.local scripts/check-model.mjs
   ```

3. 启动开发服务时采用相同的清除策略，或者在配置层明确规定覆盖优先级。
4. 让应用配置解析器只接受预期的 HTTPS host，并在缺失配置时给出不含秘密的错误码。

## 验证清单

- 清除变量前后，诊断显示的 host 或非敏感指纹发生预期变化。
- 清除后，应用调用的是 `.env.local` 指定的服务地址。
- 日志、测试输出和提交历史均不包含 API Key、令牌或完整环境文件。
- 服务从不同启动入口运行时，配置选择规则一致。

## 适用范围

适用于 Node.js 的 `--env-file`、兼容 OpenAI 的模型客户端，以及任何可能从 IDE、桌面工具或 shell 继承同名环境变量的服务。不同 Node 版本应先以最小脚本复验其覆盖规则。
