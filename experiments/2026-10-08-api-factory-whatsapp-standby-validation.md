# 实验：API Factory WhatsApp 验证的批量限制与 Standby 成本

**日期**：2026-10-08

**项目**：贸易数据助手的 WhatsApp 验证候选通道评估

**状态**：部分完成；免费配额触发后停止，未接入生产。

## 假设

1. API Factory 的单号与批量验证能复现已有校准集的注册状态。
2. Apify Standby 接口可能支持更低启动开销和多个并发请求，需要实测。
3. 结果报价能代表小规模测试的主要成本，需要与最终账务核对。

## 环境与控制变量

- 服务：Apify 商店的 API Factory「WhatsApp Number Validator (Single and Bulk)」，构建 `0.0.61`，Standby 模式。
- 账号：FREE；测试总预算 US$1。没有升级套餐或换账号绕过限流。
- 样本：同一组 14 个获准使用的号码，历史参照日期为 2026-09-29，13 个已开通、1 个未开通。本文编号 S01–S14 为脱敏引用。
- Standby 配置快照：1 GB 内存、300 秒空闲超时、每实例最大并发请求数 4、期望并发请求数 3。配置值不等于实测吞吐能力。
- 请求依次进行；先用 Python urllib，连接失败并核查日志后，另行记录 curl 测试。凭据只从仓库外的私有文件读取。
- 判据：按号码关联实际返回结果，与历史参照逐项比较；网络失败、500、429 均不能当作“未开通”。

## 对照

| 比较项 | 对照方式 | 边界 |
| --- | --- | --- |
| 注册状态 | 本次返回值与历史校准集比较 | 号码状态可能变化；历史结果不是永久真值 |
| 单号与批量 | 单查 S01、S14，再批查同一校准集 | S01 跨请求重复；不是批内去重实验 |
| 批量大小 | 14 个输入被拒后，按 10＋4 拆分 | 未测试付费账号的批量上限 |
| 网络故障 | 保留 urllib 失败，再单独记录 curl 调用 | 客户端、时间和实例均变化，不能据此证明故障根因 |
| 成本 | 结果事件、启动事件、run 总额与账号用量增量比较 | 统计口径不同，不能相加计算总费用 |

## 数据

### 调用结果

| 场景 | 观测 | 端到端耗时 |
| --- | --- | ---: |
| 单号 S01，首次启动 | HTTP 200，`valid / true`，与参照一致 | 7.834 秒 |
| 单号 S14，复用实例 | HTTP 200，`invalid / false`，与参照一致 | 4.909 秒 |
| 批量 14 个 | HTTP 500，提示最多允许 10 个；无验证结果 | 3.773 秒 |
| 批量 10 个，urllib | `URLError`；未见对应服务器验证日志或结果 | 3.015 秒 |
| 批量 4 个，urllib | `URLError`，原因记录为 `SSLEOFError`；未见对应服务器验证日志或结果 | 3.062 秒 |
| 批量 10 个，curl，新实例 | HTTP 200，S01–S10 均为 `valid`，与参照一致 | 9.504 秒 |
| 批量 4 个，curl | HTTP 429，提示免费用户响应较慢、每小时限 12 次；本批无结果 | 6.079 秒 |

共取得 **12 条成功结果、11 个不同号码**，其中 10 个已开通、1 个未开通，**11/11 与历史参照一致**。S01 在两次请求中都产生了结果计费事件。S11–S13 未完成验证。

中国 +86 样本为 S12、S13、S14；仅历史未开通的 S14 完成验证，两个历史已开通样本尚未测到。所有时延都是单次观测，包含网络和可能的冷启动；没有同一时段的旧通道性能对照。

### 限流和契约

- 14 个输入被后端拒绝，错误明确提示最多 10 个；10 个输入成功。这是本次免费通道的观测，不推广为所有套餐的上限。
- 429 来自供应商后端，发生在累计 12 条成功号码结果之后。提示中的“12 次/小时”究竟按 HTTP 请求、号码还是其他规则累计，尚未确认。
- 响应还带有 `X-RateLimit-Limit: 70`；这是另一层限制，时间窗未核定，不能解读为已验证的 70 次/分钟能力。
- 单号返回 `phone / hasWhatsapp / status`，批量返回 `phone_number / status`。需要分别解析，并核对返回号码与输入的对应关系。
- 在格式有效的负样本上，`invalid` 表示未开通。无效输入的返回语义尚未测试，不能直接套用这一含义。
- 结果没有供应商核验时间字段。本机收包时间、平台日志时间与供应商返回的核验时间应分别标记。
- README 示例地址与 Actor 元数据返回的 Standby 地址不同。本次使用元数据地址；没有验证旧地址是否仍可用。

### 费用与清理

| 口径 | 实测金额（USD） |
| --- | ---: |
| 结果事件：12 × 0.0001 | 0.00120000 |
| 启动事件：2 × 0.00005 | 0.00010000 |
| 两个 Actor run 总额，包含上述事件及资源等费用 | 0.02326032 |
| 账号用量快照增量 | 0.02383491 |

两个 run 总额在结束后再次读取，金额一致。账号用量与 run 的统计范围不同，以上金额不能重复相加。未取得结果的 500/429 没有增加结果计费事件，但实例运行和错误存储仍产生平台用量。

第一实例空闲后自动结束，第二实例在核对后主动终止，最终没有仍运行的测试实例。本次成本约 2.4 美分，主要来自运行资源；结果报价 US$0.10/千条不能代表低流量 Standby 的全部成本。没有修改生产服务或客户账本。

## 结论

1. 已完成样本支持“该接口能返回与历史参照一致的注册状态”，不支持“普遍准确率为 100%”。
2. 免费限制阻断了剩余样本和并发实验，**尚不能判断能否解决生产并发**。付费方案能力也没有得到验证。
3. 低流量 Standby 成本需要同时核算结果事件、启动、运行及空闲时间；仅比较单条报价会明显低估本次成本。
4. HTTP 状态码、成功结果条数、不同号码数、计费事件数是不同指标，必须分别记录。

## 可复用发现

- 新供应商先核对账号套餐、实际 endpoint、批量上限和响应语义，再扩大样本或并发。
- 失败请求保留原始证据与请求身份。先查日志、结果集和计费，再决定是否有必要发起新的有界实验；不能以重试成功覆盖首次失败。
- 错误脱敏保留异常类型、底层原因和 HTTP 状态。本次第一次 `URLError` 未记录底层原因，后续才补上，不能倒推第一次也是相同 TLS 故障。
- 成本实验在结束后确认实例已停止，再读取稳定的 run 费用，并单独记录账号层面的增量。
- 单号与批量都需要验证返回号码、状态与输入的对应关系；不要只检查 HTTP 200。

这些发现来自一个项目的一次有限实验，暂不提升为跨项目 Pattern。

## 未覆盖范围

- S11–S13，以及两个中国已开通样本。
- 2 个及更多并发请求的成功率、延迟和限流行为。
- 批内重复号码、无效格式、未知结果及相关计费。
- 付费账号的批量上限、请求上限、恢复窗口和长期稳定性。
- 幂等、超时后结果恢复、生产适配及与现有供应商的同条件性能比较。

当前只保留候选通道结论。后续补测应另开运行记录，继续保留本次部分完成的结论。
